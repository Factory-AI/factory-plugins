# Secrets and environment

Secrets are encrypted at rest and injected as environment variables at boot.
No Fly interface returns a secret's value; `fly secrets list` shows names,
digests and deployment status. Plain configuration belongs in `[env]` in
`fly.toml` ([configure.md](configure.md)); a secret with the same name wins.

## Inspect

```bash
fly secrets list -a <app> --json          # NAME, DIGEST, status: Deployed | Staged | Partial
fly config env -a <app>                   # runtime env names from config
```

Status markers: `*` staged (not on any Machine yet), `!` partial (rolling
deploy in progress).

MCP: `list_app_secrets`, `get_app_secret` (metadata only). Their schemas show
a `show_secrets` parameter that the server refuses with an error that reads
like a missing grant; omit it, and do not read that refusal as evidence the
grant lacks secret access.

## Set

```bash
fly secrets set KEY=value -a <app>                 # sets and deploys the current image
fly secrets set KEY=value OTHER=value -a <app>     # several at once, one restart
fly secrets set KEY=value --stage -a <app>         # stage; lands on the next fly deploy
fly secrets set KEY=value --detach -a <app>        # do not wait for the restart
fly secrets import -a <app> < .env.production      # NAME=VALUE lines from stdin
fly secrets import --stage -a <app> < secrets.txt
fly secrets deploy -a <app>                        # deploy staged secrets without a code deploy
fly secrets sync -a <app>                          # refresh flyctl's view after changes elsewhere
```

Every `set` without `--stage` restarts the app's Machines. Before a first
deploy, or when setting several values across commands, use `--stage` and let
`fly deploy` carry them. Values with special characters: quote them in the
shell, or prefer `import` from a file that is not committed.

Getting values in without exposing them:

- Read from a file the user already has (`fly secrets import < file`).
- Pipe from a secret manager (`op read ... | xargs -I{} fly secrets set
  KEY={}` is still visible in process listings; prefer `import` with a
  heredoc or file).
- Ask the user to run the command themselves when the only source is their
  clipboard. Never ask them to paste a value into chat.

In your reply, name the keys you set and the digest or status from `fly
secrets list`. Never repeat values, not even partially, and do not include
them in a confirmation prompt's reason.

MCP: `set_app_secret` (`body.value`), `update_app_secrets` (`body.values`
mapping; `null` deletes and also needs `fly:secrets:delete`; the upstream
bulk API needs create, write and delete bits even for sets, so do not work
around a rejected grant), both metadata-only results.

## Remove

```bash
fly secrets unset KEY -a <app>              # removes and redeploys
fly secrets unset KEY --stage -a <app>
```

MCP: `delete_app_secret`; deletion is idempotent and can report success for a
name that was already absent, so confirm with `list_app_secrets`.

## Build-time secrets

Deploy-time secrets are not available during the image build. Use
`fly deploy --build-secret KEY=VAL` and `RUN --mount=type=secret,id=KEY` in
the Dockerfile. Build args (`--build-arg`) are baked into the image; never
pass credentials as args.

## Files from secrets

`[[files]] secret_name = "NAME"` writes a base64-encoded secret to a path in
the Machine at deploy time, for certificates and config files. `fly machine
run --file-secret /path=NAME` does the same for one Machine.

## Common keys

- `DATABASE_URL`: set by `fly mpg attach` / `fly postgres attach`.
- `REDIS_URL`: set by `fly redis create` when attaching.
- `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`,
  `AWS_REGION`, `BUCKET_NAME`: set by `fly storage create`.
- `SECRET_KEY_BASE`, `RAILS_MASTER_KEY`, `SESSION_SECRET`: often generated by
  `fly launch` scanners.
